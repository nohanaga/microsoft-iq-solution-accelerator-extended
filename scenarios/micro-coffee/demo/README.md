# 舞黒珈琲店 デモ実演マニュアル

## サマリー

**「顧客の要望を商品案に変え、原価・在庫・供給・過去の判断を照合して、再検討の材料をそろえる」約 25 分の実演です。** EC、顧客の声、商品開発、供給と注文、Data Copilot の順に進みます。最後の結論は「条件付きで再検討できる」であり、商品化の承認・発注・実在庫の引当ではありません。

対象はこの accelerator に移植した現行画面です。2026-09-28 にソースと同梱原本を照合して作成しました。先の移植作業では主要画面の表示を確認していますが、本台本を新環境のクラウド接続込みで通して実演した結果ではありません。以下の数値は、明記した同梱データと条件に対する期待値です。

業務データ・会議・規定は合成教材です。**実在する公開データは別収録の世界銀行コーヒー価格**で、架空店舗の売上・仕入価格へ置き換えてはいません。実サービスから合成データを取得しても、実業務データにはなりません。

当日の入口: [開始前の準備](#開始前の準備) / [全体の進行](#全体の進行) / [IQ の質問](#第-5-幕-過去の却下理由と現在の条件を照合する) / [失敗時の進行](#失敗時の進行) / [終了と復元](#終了と次回への復元)。

注文保存・受注同期・音声・RTI・ML の追加実演は後述の「任意の追加実演」を使います。当日未接続の機能を本編に組み込みません。

## 開始前の準備

新環境をまだ構築していない場合は、[元データで構築してデモを実演する](../../../docs/end-to-end-setup.md) を先に実施してください。Semantic Model、Rayfin 初期データ、PostgreSQL、Foundry/IQ、受注同期の接続がそろった段階で本書へ戻ります。ローカル閲覧だけの場合は次の起動手順から始められます。

### 起動とタブ

Node.js 22.12 以上で accelerator ルートから `npm run setup:apps` を実行し、別々のターミナルで `npm run dev:storefront` と `npm run dev:operations` を起動します。導入済みなら毎回の再インストールは不要です。手順の詳細は [EC](../../../apps/storefront/README.md) と [業務アプリ](../../../apps/operations/README.md) を参照してください。

| タブ | 通常の URL / 開く場所 | 用途 |
| --- | --- | --- |
| EC | `http://127.0.0.1:5180/shop` | 商品閲覧・比較 |
| 顧客の声 | `http://127.0.0.1:4186/#/ops/reviews` | 原文と集計 |
| 商品開発 | 業務 URL の `#/ops/development/DEV-001` | 飲料の配合試算 |
| ブレンド調合 | 業務 URL の `#/ops/development/DEV-002` | 本編の原価・数量比較 |
| 供給と注文 | 業務 URL の `#/ops/supply` | 入荷・注文・予測 |
| IQ / 文書 | Data Copilot または Foundry の対象 Agent のプレイグラウンド。未接続なら本書の文書リンク | 過去の会議と現行規定 |

ポートが使用中なら、起動ログの実際の URL に読み替えます。前回の移植確認では業務画面に 4190 を使用しました。DAX を含むライブ版はローカル URL ではなく、配備済みアプリを Fabric ポータル内で開きます。[S2]

> 「舞黒珈琲店の商品企画を題材に、顧客の要望から商品案を検討します。売れそうかだけではなく、材料は足りるか、過去に同じ案が却下されていないか、規定はどう変わったかまで確認します。店舗・注文・会議は合成教材です。本日は［選択した実演形式］でお見せします。」

## 第 1 幕 EC で商品を選ぶ

**操作**

1. EC の「珈琲豆のお品書き」を開き、受取店舗と商品一覧を示します。
2. 商品カードから 2 商品を比較対象に選び、「比較する」を開きます。実際に表示された価格・味の説明・内容量を読むだけにします。
3. 商品詳細やカートを開き、購入前に確認する情報を示します。本編では注文確定しません。

**説明**

> 「顧客側では、商品を比較して選ぶ体験があります。文字・音声の相談も接続できますが、商品案の良し悪しを AI の文章だけで確定するわけではありません。注文を保存する場合は、サーバー側で商品・価格を確認します。」

**確認する結果**: 商品比較とカートの画面が表示されること。ローカル版の成功条件に AI 回答や DB 保存を含めません。文字・音声相談は任意実演へ分離します。

**次へのつなぎ**

> 「ここからは担当者の画面です。今の EC 操作が自動収集された画面ではなく、あらかじめ用意したレビュー・アンケート・SNS・会話の教材を分析します。」

## 第 2 幕 顧客の声から原文へ戻る

**操作**

1. 業務アプリの「顧客の声」を開きます。「商品」で「バニラクリーム水出し珈琲」（`PRD-002`）を選び、開始日を `2026-06-01`、終了日を `2026-07-08`、「全店舗」にそろえます。
2. 情報源を「すべて」にし、投稿数の推移・店舗別ランキング・声の傾向を示します。
3. 「要望と原文」で話題「甘さ控えめ」を選び、表示された原文を 1 件読みます。商品名・店舗・情報源・日時を一緒に確認します。
4. 話題を「全話題」に戻します。情報源を切り替える場合は、レビュー評価と評価点のない発言を同じ母集団として比較しないことを説明します。

**説明**

> 「投稿が増えたことと、買いたい人が増えたことは同じではありません。まず、どの商品について、どの発言を集計しているかを原文まで戻って確認します。『甘さ控えめ』という要求は企画の材料であって、特定の豆の配合が優れている証明ではありません。」

**確認する結果**: フィルターと原文が対応すること。話題がない、または結果が 0 件なら商品・期間・店舗・情報源・残っている語の選択を確認します。都合のよい投稿をその場で作って補いません。投稿件数を顧客人数・販売需要と呼びません。

「開発案件を開く」で商品開発へ進めます。これは画面移動であり、顧客の声から新商品が自動登録・承認される処理ではありません。[L2]

## 第 3 幕 配合・原価・在庫を比較する

> 「次は同じ企画担当者が使う、材料面の検討です。対象を別商品のオリジナルラテとブレンド候補に切り替えます。先ほどの水出し珈琲の要望から、この配合が自動生成されたわけではありません。」

### 飲料で計算の読み方を示す

1. 「飲料開発」で「初期配合に戻す」を押します。
2. 対象商品を「オリジナルラテ」、配合を「案 A」、追加製造数を `500`、製造拠点を「中央製造拠点」にします。
3. 豆の必要量 **10 kg** と、豆の原価 **47 円/杯** を示します。これは 20 g/杯、ブラジル 50%・コロンビア 50% の豆だけの税抜参考原価です。牛乳・包材・加工費を含みません。[L1]

> 「同じ数量でも、材料と配合が変われば原価と必要量が変わります。今見ているのは製造の試算で、販売価格や利益ではありません。」

### ブレンドの案 A と案 B を比較する

1. 「ブレンド調合」へ移動し、「初期配合に戻す」を押します。
2. 「オリジナルブレンド」、`100` 袋、「中央製造拠点」、「案 A」を指定します。豆の必要量 **20 kg**、豆の原価 **470 円/袋** を確認します。
3. 「案 B」を選びます。エチオピア 60%・グアテマラ 40%、豆の必要量 **20 kg**、豆の原価 **608 円/袋** を確認します。
4. 「豆の必要量と在庫」で、在庫残高と確保済みを区別して読みます。下表は同梱の固定データに対する期待値です。

| 案 B の豆 | 比率 | 必要量 | 利用可能 | 不足 | 製造後の計算上の残り |
| --- | --- | --- | --- | --- | --- |
| エチオピア | 60% | 12 kg | 12 kg | 0 kg | 0 kg |
| グアテマラ | 40% | 8 kg | 18 kg | 0 kg | 10 kg |

「残り」は利用可能量から今回必要量を引いた説明用の値です。実在庫の更新結果ではありません。基準日時と取得元を確認し、ライブ値が異なる場合はこの表を正解として押し付けず、当日の値で計算し直します。[L1]

> 「案 B は、この固定時点の数量条件では 100 袋分を計算できます。ただしエチオピア豆の余裕はゼロです。『不足なし』と『余裕がある』は違います。香り重視という名前だけで品質評価が済んだことにもなりません。」

### 200 袋に増やして反証する

1. 「追加製造数」を `200` にします。
2. 必要量 **40 kg**、エチオピア必要 **24 kg**・不足 **12 kg**、グアテマラ必要 **16 kg**・残り **2 kg** を確認します。単位当たりの豆原価は **608 円/袋** のままです。
3. 数量を `100` に戻します。第 5 幕まで「案 B / 100 袋」を維持します。

> 「100 袋のときの判定を、200 袋へ流用しません。数量を変えると不足が現れるので、企画と調達の相談が必要になります。」

### 関係と保存の境界を示す

「配合と産地のオントロジー」で配合・豆・産地をたどります。ライブ版で Fabric Graph が利用できる場合だけ「この豆はどこまで影響するか」の取得結果を説明します。メモリーモードの関係図を、Graph の実照会結果とは呼びません。関係があることだけで供給停止の原因や代替品の適格性を断定しません。

保存は任意です。「配合を保存」はメモリーモードならメモリー、ライブなら SQL への下書き保存です。商品化承認や製造指図ではありません。ライブ保存はデモ専用環境で事前承認がある場合だけ行います。[L3]

## 第 4 幕 供給と注文を確認する

**操作**

1. 「供給と注文」を開き、「実績」の画面で全店舗・全供給会社の集計を示します。日付条件が残っている場合は現在の条件を読み上げます。
2. 「店舗別の状況」で神田店など 1 店舗を選び、入荷・遅延・注文の内訳を見ます。
3. 入荷便の一覧またはフローから 1 便を選び、予定と到着の時刻を比較します。注文の一覧でも状態と商品額を確認します。
4. 「機械学習の予測」「需要予測」「入荷の遅延リスク」が表示される場合は、実績とは別のモデル出力であることを示します。

**説明**

> 「製造案が数量条件内でも、実際の店舗への入荷や注文は別に確認します。過去の入荷実績と、モデルの遅延予測は分けて読みます。予測確率だけで注文をキャンセルしたり、在庫を変更したりはしません。」

**確認する結果**: 選択した店舗・便・期間が明細と一致すること。同梱予測は保存済みのモデル出力で、その場で再学習・推論した結果ではありません。ライブで予測テーブルが利用できない場合は、予測なしの説明に切り替えます。[L4]

本編では供給停止や引当の保存操作を行いません。「対応検討」「停止・受注引当」は別の操作範囲です。ブレンド試算の豆在庫と店舗の全商品・全注文が完全に対応しているとは説明しません。

## 第 5 幕 過去の却下理由と現在の条件を照合する

ここから扱う案件は **香り重視ブレンド `IDEA-BLEND-AROMA`** です。第 2 幕の飲料の甘さに関する声と同一案件として結び付けません。「商品の別の例として、ブレンドの過去判断を調べます」と区切ります。

### 質問 1: 同じ案は以前にも出ていたか

ブレンド画面の Data Copilot、または対象 Agent の新しいプレイグラウンド会話に送信します。

```text
MAIKURO-V3-DEMO の香り重視ブレンド IDEA-BLEND-AROMA は、過去の会議で既に提案されていましたか。提案内容、会議日、決定、却下理由を Work IQ で調べてください。後続の会議があれば状態の変化も示してください。本文の業務日を使い、実掲載日だけで期間を限定しないでください。会議の出典と原文リンクを付けてください。
```

**司会者の照合点**: [WQ-001](../knowledge/work-iq/WQ-001-blend-rejection.md) の D-0618 と [WQ-002](../knowledge/work-iq/WQ-002-blend-reconsideration.md) の D-0707。6 月 18 日は、608 円/袋が上限 550 円を **58 円超過**し、エチオピア豆が必要 12 kg に対し 8 kg で **4 kg 不足**して却下。7 月 7 日は再検討の方針ですが、試作・商品化は未承認です。

> 「過去の却下理由は原価と数量でした。味が悪かったと推測せず、当時の議事録に戻ります。」

実検索では引用先を開いて本文を示します。ローカル版では上の文書リンクを直接開き、「同梱原稿を手動で照合しています」と伝えます。[WQ-003](../knowledge/work-iq/WQ-003-other-product.md) の別商品の冷蔵保管問題を、本件の理由として混ぜません。

### 質問 2: 現在有効な規定は何か

```text
MAIKURO-V3-DEMO の同じ香り重視の限定ブレンド候補について、2026-07-08 18:00 JST に有効な豆原価の規定と、再提案のマニュアルを Foundry IQ で検索してください。却下当時の規定との違い、適用区分、条項、版、有効日を示してください。上限内なら試作や商品化を承認してよいのかも確認してください。
```

**司会者の照合点**: [FQ-001](../knowledge/foundry-iq/FQ-001-cost-policy-v1.md) 第 2 条、[FQ-002](../knowledge/foundry-iq/FQ-002-cost-policy-v2.md) 第 2～5 条、[FQ-003](../knowledge/foundry-iq/FQ-003-reproposal-manual.md) 手順 2～5。7 月 1 日施行の 2.0 は、香り重視の限定候補のみ上限 **650 円/200 g 袋**。通常候補は **550 円** のままです。上限内でも承認ではありません。

> 「変わったのは限定候補の規定です。豆の単価が下がったわけではなく、通常品の上限も変わっていません。」

会議の記憶だけで答えた応答を、規定の検索成功とは扱いません。IQ 接続版では実際の検索と条項の引用を確認します。

### 質問 3: 今回は再検討できるか

「案 B / 100 袋 / 中央製造拠点」に戻っていることを確認します。**次の条件は司会者が手動で渡す画面条件**です。自動で現在の DB や画面を読んだという説明には使いません。ライブの値が異なる場合は画面と同じ値・日時へ置き換えてから入力します。

```text
MAIKURO-V3-DEMO の IDEA-BLEND-AROMA を再検討します。
以下は同梱データに基づき司会者が手動で渡す画面条件で、検索で取得した現在値ではありません。
業務基準日時: 2026-07-08 18:00 JST。合成データ。
開発商品 DEV-BLEND、配合 BLEND-B、中央製造拠点 CENTRAL、100 袋、200 g/袋。
エチオピア豆 ROASTED-ET: 60%、税抜 3200 円/kg、在庫 12 kg、確定引当 0 kg。
グアテマラ豆 ROASTED-GT: 40%、税抜 2800 円/kg、在庫 18 kg、確定引当 0 kg。
画面の豆原価は 608 円/袋、必要量 20 kg、不足 0 kg です。
過去の会議と現行規定を検索して根拠を確認し、この配合で 100 袋を再検討できるかを
「過去の却下理由 / 今回変わった条件 / 残る未確認事項」で比較してください。
原文の出典、数量・原価の計算、根拠の取得元を分けて示してください。
承認や発注はしないでください。
```

| 論点 | 当時 | 今回の条件 | 照合する根拠 |
| --- | --- | --- | --- |
| 豆原価 | 608 円、上限 550 円、58 円超過 | 608 円、限定候補の上限 650 円、余裕 42 円 | WQ-001、FQ-001、FQ-002、手動入力条件 |
| エチオピア豆 | 必要 12 kg、使用可能 8 kg、不足 4 kg | 必要 12 kg、利用可能 12 kg、不足 0、残り 0 | WQ-001、手動入力条件 |
| グアテマラ豆 | 必要 8 kg を確保できる見込み | 必要 8 kg、利用可能 18 kg、残り 10 kg | WQ-001、手動入力条件 |
| 判断 | 当時の提案を却下 | 再検討の材料はそろうが、試作・商品化は未承認 | WQ-002、FQ-002 第 5 条、FQ-003 |

**追加の一問**: 「では同じ配合で 200 袋なら？」と聞き、エチオピア豆の不足 **12 kg** を答えるか照合します。「通常ブレンドとしてなら？」には現行でも **58 円の上限超過**です。回答が条件を取り違えた場合は、その場で指摘し、引用・計算へ戻ります。期待文を代わりに表示して成功扱いにはしません。

### 締めの説明

> 「過去の却下記録は消していません。当時の理由と規定改定、今回の数量条件を並べた結果、再検討の材料ができました。ただしエチオピア豆に余裕はなく、官能評価、総原価、製造直前の在庫、担当者の承認は残っています。AI が承認を代行したわけではありません。」

聴衆に残すのは、結論だけでなく **根拠文書・適用時点・計算条件・未確認事項**の四つです。

## 実在する公開データを示す追加説明

> 「こちらは合成ではなく、出典を追跡できる公開価格です。一方、先ほどの 3,200 円/kg は合成の焙煎豆参考単価です。国際価格を為替換算しただけでは、品質・焙煎・運賃などを含む店舗の仕入価格にはなりません。」

この追加説明は文書・データ原本の閲覧です。現在の業務画面に世界銀行価格が自動表示・自動反映されるデモではありません。公開データを実在店舗の取引データと紹介しません。

## 失敗時の進行

| 状況 | 確認・復旧 | 聴衆への説明 |
| --- | --- | --- |
| ページが開かない | 起動ログの URL、ポート、対象アプリを確認 | 起動に問題があると伝え、取得済み結果に見せかけない |
| 顧客の声が 0 件 | 商品・期間・店舗・話題・語・情報源を戻す | 条件に該当する投稿がないことと全体に声がないことを区別 |
| 原価・在庫が期待値と違う | 商品、案、数量、拠点、カスタム配合、データ版を確認 | ライブ値が変わった場合は当日の値を使う |
| 配合合計が 100% でない | 対象の登録案を選び直す | 計算が止まる理由を説明する |
| 在庫が未確認 | 不明を維持し、数量判断を保留 | 不足ゼロ・生産可能とは言わない |
| DAX が取得できない | Fabric ポータル内か、Build / Read 権限、テナント設定を確認 | ローカル表示へ変更するならモード変更を明示 [S2] |
| Graph / Foundry にサインインできない | 対象テナント、アプリ登録、同意、許可 URI を確認 | 接続未確認として該当区間を省略 |
| IQ の片方だけ失敗 | 取得できた文書と未取得の文書を分ける | 「過去の却下なし」「規定なし」とは断定しない |
| 引用先を開けない | 同じ利用者の原文閲覧権限を確認 | 出典確認が未完了と伝える。別利用者の権限で隠れて補わない |
| 保存結果が不明 | 記録を読み戻してから再操作を判断 | 成功や失敗を推測せず、その場の追加書込みを止める |

公式の SSO 要件は [Fabric 認証](https://learn.microsoft.com/en-us/fabric/apps/fabric-authentication) を参照してください。Rayfin のポップアップ SSO が使えることと、DAX が Fabric ホスト外で使えることは別です。

## 終了と次回への復元

1. ブレンドを案 B・100 袋へ戻した後、次回の開始用には「初期配合に戻す」で案 A・100 袋へ戻します。飲料も初期配合へ戻します。
2. 店舗・話題・期間などのフィルターを次回の開始条件へ戻し、残った商品比較・カートを確認します。保存済みの条件が不明ならデモ専用の新しいブラウザープロファイルを使います。
3. 音声接続とマイクを停止し、共有端末では各サービスからサインアウトします。開発サーバーを止めるときは各ターミナルで Ctrl+C を使います。
4. 実 DB に保存した合成注文・試算の ID を記録します。記録の一括削除や共有 DB の初期化は行いません。クラウド資源を作成した場合の費用・停止は配備手順に従って別途管理します。
5. メモリーモードの試算保存は、そのリポジトリインスタンス内だけです。永続保存や次回の再開を前提にしません。[L3]
